> 依据项目文档 `project.md` 编写。版本 v1.1，日期见文件系统时间。
> 前提假设：1–2 名工程师全职。
> 已确认的决策（v1.1）：本期只做 Windows；虚拟摄像头必须内嵌进工程、零配置可用；里程碑按"M1 最小闭环先行"执行。Linux/Android 不在当前范围，核心层保持平台无关仅为将来留口，不为它们投入。

## 一、总体评估

**结论：项目可行，架构方向正确（核心层 + 平台适配层），模块划分与阶段划分合理。真正的风险不在动捕推理，而在"虚拟摄像头"与"性能指标达成"两块。**

对照同类成熟产品（VTube Studio、PrprLive、Veadotube）可以确认整条管线是成立且被市场验证过的：

`摄像头采集 → 人脸/姿态推理 → 参数映射 → Live2D 渲染 → 双输出`

### 1.1 文档中"建议保持"的部分

| 条目 | 评价 |
|---|---|
| 核心层 + 平台适配层分层 | 正确，务必坚持。核心逻辑（推理调度、求解、映射、渲染抽象）不碰平台 API |
| Windows → Linux → Android 顺序 | 正确。Windows 是主战场，Linux 验证可移植性，Android 裁剪版用 RTMP 替代虚拟摄像头是合理路线 |
| 两个输出通道抽象 | 正确。虚拟摄像头和浮窗应各自实现为"推帧"接口，上层统一 |
| 性能指标可量化 | 好，但部分指标偏紧（见 1.3） |
| 先打通最小闭环，再加功能 | 正确，下文里程碑据此展开 |

### 1.2 文档中"需要修正或补充认知"的部分

| 条目 | 文档说法 | 现实评估 |
|---|---|---|
| 虚拟摄像头"优先系统官方方案" | 优先调用系统级能力 | Windows 不存在公开的"官方虚拟摄像头 API"。Media Foundation 不提供通用虚拟采集设备；Windows Studio Effects 的背景虚化仅限 Copilot+ PC 且只作用于系统采集管线，不适用于自研合成输出。这条约束必须改写为实际可行的路线：**免驱动用户态 DirectShow filter 优先，内核驱动方案备选**（详见第四节） |
| 背景虚化"优先系统级能力" | 同上 | 现实是**软件分割为主**。MediaPipe Image Segmenter / Selfie Segmentation 在 GPU 上约 5–10ms/帧，完全满足"帧率下降不超过 10%"的约束。系统级能力作为加分项保留，不作为依赖 |
| 时间估算 8+4+2 周 | 文档原文 | 偏乐观。虚拟摄像头兼容性排查通常是一到两周的独立专项，不应计入主线。建议里程碑改为最小闭环优先（见第六节） |
| 动捕精度"暗光下效果下降"归为风险 | 对 | 但应对方案（亮度提示、曝光调节）目前无软件细节，需要补充：分辨率自适应降级 + 可视化置信度提示 |

### 1.3 关键风险评级

| 风险 | 等级 | 说明与对策 |
|---|---|---|
| 虚拟摄像头兼容性（OBS/Teams/Zoom/会议软件） | 高 | 各软件对虚拟设备的要求不一（格式、帧率协商、签名）。对策：一期锁定用户态 DirectShow 方案 + 兼容性矩阵测试；保留驱动路线备选 |
| 端到端延迟 < 120ms | 中 | 可达成，但依赖 GPU 推理 + 渲染直通，且要避免虚拟摄像头缓冲过大。对策：管线设计为"推帧不排队"，虚拟摄像头内部缓冲控制在 1 帧以内 |
| 启动时间 < 3s | 中 | 模型加载（Live2D + 推理模型）是主要耗时。对策：启动即预热动捕模型、Live2D 模型懒加载；固态硬盘环境实测 |
| CPU < 25% / 内存 < 800MB | 中 | 推理走 GPU delegate、渲染 D3D11 时可达成；MediaPipe 模型小，纹理占用可控。达标需要专门压测 |
| Cubism SDK 授权 / 模型版权 | 低 | Cubism SDK 免费（含商用），但需遵守其条款（不重新分发 SDK、保留版权声明）；用户自有模型需单独确认授权。交付物中示例模型需用自带授权样本 |
| Linux 内核模块安装门槛 | 中 | 按文档要求提供一键安装脚本（v4l2loopback），符合预期，非阻塞 |

## 二、技术选型建议

### 2.1 总体

```
语言：      C++17 核心库（本期只做 Windows；核心保持平台无关，为将来留口）
UI：        Qt 6（QWidget，本期仅 Windows）
推理：      MediaPipe Tasks Vision（Face Landmarker + Pose Landmarker）
Live2D：    Live2D Cubism SDK for Native 5.x（C++ Core）
渲染：      D3D11 后端；浮窗用 DirectComposition 合成
虚拟摄像头： 内嵌 DirectShow 用户态 filter（共享内存喂帧），首次运行自动注册，零配置
背景分割：   MediaPipe Image Segmenter（软件），系统级能力为加分项
```

### 2.2 各层选型理由

| 层 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 语言 | C++17 | Cubism Core 只有 C/C++ 官方绑定；MediaPipe C++ API、DirectShow、v4l2loopback 全是 C/C++ 生态。C#/.NET 需多层 P/Invoke 封装，成本高 | Rust（生态尚不成熟，不推荐一期） |
| UI 框架 | Qt 6 Widgets | Win/Linux 一套代码；QWidget 天然贴近"桌面工具"质感，易做像素级控制与暗色主题；托盘、快捷键、多屏支持成熟 | QML（浮窗动画更顺，但控制性弱）；WPF/WinUI（放弃 Linux 复用） |
| 推理 | MediaPipe Face Landmarker | 直接输出 478 关键点 + 52 个 ARKit 风格表情系数，把"关键点→表情参数"的求解工作量砍掉大半；CPU 约 5–15ms/帧，GPU 更快；Apache 2.0 协议宽松；官方支持 Win/Linux/Android | ONNX Runtime + 自选模型（定制性强，但求解要自研，工作量 +2 周） |
| Live2D 渲染 | Cubism SDK for Native | 官方唯一正规路径；自带多平台后端（OpenGL/D3D9/D3D11/Metal/Vulkan），契合"渲染后端抽象" | 第三方渲染器（UNIA 等）不受控，不推荐 |
| Windows 浮窗 | D3D11 + DirectComposition | 支持逐像素透明 + 低延迟合成；WS_EX_TRANSPARENT 实现点击穿透；与 Cubism 的 D3D11 后端天然衔接 | WS_EX_LAYERED + UpdateLayeredWindow（兼容性兜底） |
| 背景分割 | MediaPipe Image Segmenter | 单模型即得高质量人体 mask；GPU 上开销小；可直接复用采集帧 | 深度学习自研分割（没必要） |

### 2.3 平台适配层接口清单（核心抽象，文档 2.1 的落地）

```
ICaptureSource    采集：枚举设备、打开、开始/停止、帧回调（分辨率/帧率可配）
IVirtualCamera    输出通道A：注册设备、推帧（格式协商、缓冲策略）
IFloatingWindow   输出通道B：创建透明窗口、推纹理、穿透/缩放/位置记忆
IGPUContext       纹理与渲染上下文抽象（D3D11 / GLES / OpenGL）
IRenderBackend    渲染后端抽象（Cubism 后端 + 合成）
```

新增平台只需实现这 5 个接口。**本期只实现 Windows 版**；Linux/Android 的接口保留定义，不投入实现。

## 三、核心管线设计

### 3.1 动捕管线（采集 → 推理 → 求解 → 映射）

```
摄像头帧 (NV12/BGR)
  → 人脸追踪：MediaPipe Face Landmarker（多脸检测，取最大脸）
      输出：478 关键点 + 52 blendshape（眼、嘴、眉、下巴全部覆盖）
  → 姿态追踪：MediaPipe Pose Landmarker（仅上半身 17 点）
      输出：肩颈/躯干旋转与位移
  → 求解模块（纯逻辑，平台无关）：
      头部旋转：关键点三角测量（P3P 或平面假设 + 经验标定）
      表情系数：直接映射 blendshape → Live2D 参数（可配曲线）
      上半身：肩线斜率 → 躯干旋转，颈部向量 → 颈部旋转
      平滑：指数平滑 + 动作灵敏度阈值，快速动作做延迟补偿（文档 3.2 要求）
  → 映射模块：参数名表（Live2D 模型 param 名 ↔ 语义参数），带映射曲线
```

要点：

- **最大人脸选择**：MediaPipe 返回多脸，按包围盒面积取最大，其余丢弃（满足文档 3.1 多人场景要求）。
- **求解与映射分离**：求解输出"语义参数"（头 Yaw/Pitch/Roll、嘴开合、眨眼……），映射层负责把语义参数换算成具体模型的 param 名与数值。这样换模型不需要重写求解。
- **延迟目标**：推理本身（face ~8ms、pose ~10ms，GPU 更低）远低于 50/80ms 约束；余量留给采集与渲染。端到端 120ms 的关键是把虚拟摄像头缓冲压到 1 帧。

### 3.2 渲染管线

```
Live2D 模型加载（Cubism Core）
  → 每帧：写入语义参数 → 更新模型 → 渲染到 GPU 纹理（透明背景）
  → 合成：底层 = 摄像头帧（可选高斯模糊 + mask 羽化），上层 = 模型纹理
  → 输出：推给浮窗（DirectComposition）/ 虚拟摄像头（格式转换 YUY2/NV12）
```

- 抗锯齿：D3D11 MSAA 或后处理 FXAA，模型边缘质量优先。
- 模型切换：Cubism 支持运行时换模型，预加载两份或异步加载均可，文档要求"无需重启"可直接满足。
- 高 DPI：Qt 侧开 `AA_EnableHighDpiScaling`（Qt6 默认），浮窗渲染按物理像素输出。

### 3.3 输出通道

**通道 A 虚拟摄像头**（详见第四节）

**通道 B 桌面浮窗**：

- 无边框、透明、置顶：`WS_EX_LAYERED | WS_EX_TOPMOST`，通过 DirectComposition 的 swapchain 呈现每帧。
- 点击穿透：`WS_EX_TRANSPARENT` 切换；穿透模式下浮窗自身不响应鼠标，靠"悬浮工具条"（非穿透区域）操作，或热键切换。
- 拖动 / 缩放：非穿透模式按住拖动，滚轮缩放；状态持久化到配置（退出记忆位置与大小，满足文档 3.4）。
- 多显示器：记录上次显示器 + 允许热键在显示器间移动。
- 独立线程渲染，不占主线程（文档 3.4 性能要求）。

## 四、虚拟摄像头专项（最高风险，单列）

### 4.0 需求确认：内嵌、零配置

用户已明确：虚拟摄像头必须"塞进工程、无任何配置操作"。即用户感知只有一层——安装并运行本软件后，OBS/Teams/浏览器里就多了一个摄像头设备，不需要安装驱动、不需要打开注册界面、不需要任何设置项。

落地方式：

- **自注册 DirectShow filter**：应用未检测到虚拟设备时，首次运行自动把 filter DLL 复制到应用目录并调用 `DllRegisterServer` 完成注册（优先 HKCU 用户态视图，无需管理员权限；失败时提示一次以管理员重试）。
- **自愈**：每次启动检查设备是否可枚举；缺失则自动重注册并重启枚举线程，全程无弹窗，状态栏记录一条日志。
- **界面不出现"设备未注册/安装引导"类配置**：输出页只有一个开关。开关状态与注册状态联动，注册失败仅在状态栏给出可点击的错误说明。

### 4.1 现实约束

- Windows 无官方虚拟摄像头 API。可选的只有第三方方案。
- 各消费软件对虚拟设备的兼容阶梯大致为：**内核驱动设备 > 用户态 DirectShow filter > 捆绑 OBS 的方案**。Teams/Zoom 对"非签名驱动/特殊格式"有明显限制，但用户态 filter 在 OBS、会议软件、浏览器中普遍可用。

### 4.2 推荐路线

| 路线 | 实现 | 优点 | 缺点 | 定位 |
|---|---|---|---|---|
| A：用户态 DirectShow filter | 自研或基于开源 DirectShow 虚拟摄像头（如 virtualcamdshow 思路）：应用进程渲染完成后把帧写入共享内存，filter 侧按需读取并提供标准 VS/YCbCr 输出 | 无需驱动签名，安装即注册，兼容 OBS/常见会议软件 | 部分 App 对用户态 filter 协商支持略弱 | **一期首选** |
| B：内核驱动虚拟设备 | 基于开源 usbcam 同类内核驱动方案，需 WDK 构建与驱动签名 | 兼容性最好，浏览器/Teams 通吃 | 签名证书成本、安装门槛、驱动崩溃风险 | 二期/按需备选 |

### 4.3 专项计划

1. 第 0 周：搭建 DirectShow filter 骨架 + 共享内存协议，先做到"输入固定测试帧，OBS 能识别并出画面"；同步落地 4.0 的自注册与自愈逻辑。
2. 兼容性矩阵：OBS / Streamlabs / Zoom / Teams / 腾讯会议 / 钉钉 / 浏览器 WebRTC，逐个验证并记录格式协商差异。
3. 格式支持：优先 YUY2 与 NV12 双格式，分辨率 720p/1080p 按协商切换（文档 3.3）。
4. 缓冲策略：filter 侧缓冲 ≤ 1 帧，避免拖高端到端延迟。
5. 边界情况：无消费者时不推帧（省 CPU）、消费者断开自动重连（文档 4.4 稳定性）。

## 五、非功能需求落地清单

| 指标 | 达成路径 |
|---|---|
| 动捕 ≥ 25 FPS | GPU delegate 推理 + 双缓冲采集，实测留 1.5 倍余量 |
| 端到端 < 120ms | 计算预算：采集 ≈ 10ms、推理 ≈ 15ms、渲染/合成 ≈ 10ms、输出 ≈ 10ms（虚拟摄像头 1 帧缓冲）；总预算 45–60ms，留一半余量 |
| CPU < 25% / GPU < 30% | 推理走 GPU；CPU 侧只做帧搬运与逻辑；压测达标为准 |
| 内存 < 800MB | D3D11 纹理池复用，不每帧分配；MediaPipe 模型驻留 ~50MB 内 |
| 启动 < 3s | 启动即预载推理模型；Live2D 模型"选择后才加载"或异步预载；首帧输出前置 |
| 8 小时稳定 | 每帧零分配、纹理复用、显存及时释放；摄像头断开自动重连 + 推理异常降级（改跟随上次参数）不中断输出（文档 4.4） |

## 七、UI 设计规范（按需求：无 emoji、简约清晰、黑色系、易操作、去 AI 味）

### 7.1 设计原则

1. **这是桌面工具，不是营销页。** 参照 OBS、专业音视频工具的质感：flat、低装饰、信息密度合理，一切为"快速找到开关、看清状态"服务。
2. **去 AI 味的定义**（本项目的硬性检查清单）：

禁止出现：
- 所有 emoji / 表情符号（包括状态图标位置，一律用几何图形或文字）
- 紫色/靛蓝渐变、玻璃拟态（frosted glass）、泛光、弥散光斑
- 大圆角卡片（圆角 ≤ 4px）、悬浮阴影、装饰性渐变背景
- "智能""AI 驱动""轻松开启""一键玩转"等营销文案
- 无意义的装饰图标堆砌；图标只在与功能强相关时使用 <2px 线性图标>
- 中心化 hero 式欢迎页、超大白边留白、大号渐变标题
- 感叹号堆叠、emoji 化空状态（如"暂无模型 😢"，改为纯文字）

采用：
- 平面、直角或 2–4px 圆角、1px 分隔线、极轻阴影或不用阴影
- 单一强调色 + 三个状态色；黑底不下沉到全黑，用带微弱冷调的分层黑
- 真实数据实时可见（FPS、延迟、格式、分辨率），这是去 AI 味的最强信号
- 默认配置即合理：启动即用，无需读文档

- 左导航 160px：纯文字条目，选中态 = 强调色左侧 2px 竖条 + 文本高亮，无图标。
- 顶栏唯一的强调动作是"开始/停止"，窗口其余部分不抢视觉。

### 7.4 组件清单（按页面）

| 模型 | 左侧模型列表（缩略图 + 名称 + 状态点）；右侧参数面板：分组滑杆（表情 / 头部 / 身体），每项含参数名、当前值、重置按钮；底部"切换模型"即时生效 |

- 开关控件：统一用"拨动开关"（黑色系，开 = 强调色填充，关 = 控件底色），全应用一致。
- 滑杆：细轨 + 小圆钮，聚焦时有强调色描边；数值实时显示在右侧等宽字体。
- 空状态：纯文字 + 一个明确的行动按钮（"添加模型""选择摄像头"），不加装饰图。

### 7.5 交互规则

- 一键启动：启动自动加载上次预设并开启动捕与输出（文档 3.6）；首次启动有 3 步最小引导（选摄像头 → 选模型 → 开始）。
- 键盘可达：Tab 顺序合理、Enter 触发、Esc 关闭弹窗；快捷键：Ctrl+Enter 开始/停止、Ctrl+F 切换浮窗穿透。
- 错误不弹窗轰炸：状态栏红点 + 点击展开详情（"摄像头已断开，正在重连"）。
- 所有状态切换（启动/停止/切换模型/换摄像头）有明确视觉反馈，且"进行中"状态用状态栏文本而非转圈动画堆叠。
- 浮窗本体：平时只有模型；鼠标悬停出现 3 个 20px 极简按钮（拖动 / 穿透 / 关闭），半透明，失去焦点即隐藏。

### 7.6 文案规范

- 动词开头、短句："开始动捕""切换模型""保存预设"。
- 状态句用固定结构：`动作 + 对象 + 结果`，如"动捕运行中 · 28 FPS""摄像头已断开，等待重连""模型参数已重置"。
- 禁用营销句、感叹号堆叠、谐音梗、emoji 替代文字。
- 数字统一等宽字体显示（FPS、延迟、分辨率），强化工具感。

### 7.7 UI 实现说明

- Qt 6 + QSS 实现上述视觉；全部颜色收敛为 7.2 的变量表，禁止散落的硬编码色值。
- 浮窗不经过 QWidget 绘制，走 DirectComposition 直通，保证透明与性能。
- 所有高频变化的面板（FPS 等）用去抖刷新（≥ 4Hz），不逐帧刷 UI。

### 10.2 关键指标（合成信号，640×480，并行推理 + pose-every-2）

- 端到端瞬时延迟 28–43ms，窗口帧率约 24 FPS（推理 15.6ms/帧：face 2.0ms + pose 13.3ms）
- 冷启动首帧 3.9–4.7s（模型加载，M4 启动优化项）
- 目标 25 FPS / 120ms 为 M4 验收项，当前 640×480 已接近

### 10.3 工具链约束（踩坑记录，务必遵守）

1. **CRT 必须与 Qt 官方 mingw 构建一致（msvcrt）**。用 UCRT 版工具链编译 exe 时，Qt 头内联代码（如 `QByteArray` 析构 → `free`）会用 exe 的 UCRT 堆去释放 Qt DLL（msvcrt 堆）分配的内存，进程启动即崩（`Invalid address specified to RtlFreeHeap`）。工具链统一为 **winlibs msvcrt 版**（`D:\deps\mingw_msvcrt`），`scripts/build.ps1` 已按此优先。
2. **运行时 PATH 顺序**：MinGW bin（GCC16 运行时）必须在 Qt bin（GCC13 运行时）之前，否则加载器取到旧版 `libgcc_s_seh-1.dll / libstdc++-6.dll / libwinpthread-1.dll`，线程入口解析失败导致 0xC0000139。
3. 运行 UI 前在 PATH 中带上两个 bin 目录；exe 目录内不宜放 windeployqt 拷贝的 GCC13 运行库（会覆盖 2 的顺序）。
4. 本机缺少视频格式转换 MFT（`MF_E_TOPO_CODEC_NOT_FOUND`），采集一律取设备原生 NV12/YUY2 并库内自转 BGRA。

### 10.4 真实摄像头（HP Wide Vision 5MP，VID_05C8）

- 仅 NV12 可用：`lb_win: capture format=NV12 640x480`，150 帧全部处理，瞬时延迟 33–45ms，约 15 FPS（NV12 转换 + 推理开销）。
